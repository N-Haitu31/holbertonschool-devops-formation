# 0-persistence.md

## Commands

```
# 1. Run Postgres with a named volume
docker run -d --name pg-test -e POSTGRES_PASSWORD=toto123 -v pgdata:/var/lib/postgresql/data postgres:16

# 2. Write some data
docker exec -it pg-test psql -U postgres -c "CREATE TABLE test (id serial, value text); INSERT INTO test (value) VALUES ('hello');"

# 3. Verify the data is there
docker exec -it pg-test psql -U postgres -c "SELECT * FROM test;"

# 4. Remove the container
docker rm -f pg-test

# 5. Recreate the container, reusing the same named volume
docker run -d --name pg-test -e POSTGRES_PASSWORD=toto123 -v pgdata:/var/lib/postgresql/data postgres:16

# 6. Verify the data survived
docker exec -it pg-test psql -U postgres -c "SELECT * FROM test;"
```

## Observations
 
- Step 1 : Creates a container named `pg-test` from the `postgres:16` image. `-e POSTGRES_PASSWORD` and `-v pgdata:/var/lib/postgresql/data` are two independent flags in the same command, not related to each other: `-e` sets the authentication password Postgres uses to initialize itself, while `-v` separately mounts a named volume called `pgdata` at the exact path where Postgres stores its actual data files. `docker run` returned the new container's ID (`46f1d6145509...`).
 
- Step 2 : Creates a `test` table with two columns (`id`, auto-generated by `serial`, and `value`, a text field) and inserts one row with `value = 'hello'`. The output confirms this: `CREATE TABLE` acknowledges the table creation, and `INSERT 0 1` confirms exactly one row was inserted (the `0` is a legacy OID field, not meaningful here).
 
- Step 3 : Confirms the row is readable: `SELECT * FROM test;` returns `id=1 | value=hello`. At this point the container is still running with its volume attached, so nothing surprising yet — the real test is what happens after removal.
 
- Step 4 : Removes the `pg-test` container entirely (`-f` forces removal even while running). This destroys the container itself, but not the `postgres:16` image and not the `pgdata` volume — these are three independent Docker objects with separate lifecycles.
 
- Step 5 : Recreates a brand new container, also named `pg-test`, using the exact same `docker run` command — critically, reattaching the same named volume `pgdata`. Docker confirmed this by returning a **different** container ID (`ed700692932b...`), proving this is a genuinely new container, not the old one restarted.
 
- Step 6 : Is the actual proof: querying the new container returns the exact same row, `id=1 | value=hello`. Despite the container being brand new (different ID, fresh internal filesystem), the data written before deletion is still there.
 
## Conclusion
The data was never stored inside the container's own filesystem — it lived in the named volume `pgdata` the whole time. Removing and recreating the container only replaces the container; the volume, and the data inside it, is a separate object that persists independently. This is exactly what distinguishes a named volume from data written to a container's writable layer, which would have been lost on `docker rm`.
